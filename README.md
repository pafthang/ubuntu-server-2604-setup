# Ubuntu server 2604 setup

Первичная настройка чистого Ubuntu Server (24.04+, включая 26.04)
одной командой или двумя шагами:

- базовые пакеты и инструменты диагностики;
- оболочка **fish** (автоподсказки из коробки) + fzf, zellij, micro, helix;
- firewall **UFW**, защита от брутфорса **fail2ban**, автообновления security,
  персистентный журнал, опциональный swap.

**Доступом по SSH скрипты сознательно не управляют**: ключи и запрет паролей
задаются при создании сервера (панель провайдера / cloud-init) — см.
[«Почему скрипты не управляют входом»](#почему-скрипты-не-управляют-входом).

Все скрипты **идемпотентны**: обрыв связи посреди прогона лечится повторным
запуском — продолжится с того же места без дублей.

> Работает под root на свежеустановленной системе. Ничего, кроме описанного,
> не трогает; все изменения — отдельными файлами (drop-in конфиги), родные
> конфиги дистрибутива не перезаписываются.

---

## Требование к серверу

Машина должна быть создана уже с входом по ключу:

- панель провайдера (поле «SSH-ключ» при создании дроплета/VPS), либо
- cloud-init (`users.ssh_authorized_keys`), либо
- вручную перед запуском: дописать свой `~/.ssh/id_*.pub` в
  `/root/.ssh/authorized_keys`.

Проверьте до запуска: `ssh root@<ip>` впускает молча, без пароля.
Скрипты это состояние изменяют только в сторону ужесточения сети
(порт, firewall), но не аутентификации.

## Быстрый старт

### Вариант A — одной командой

Надёжнее — скачать, пробежать глазами, запустить:

```bash
curl -fsSL https://raw.githubusercontent.com/pafthang/ubuntu-server-2604-setup/main/bootstrap.sh \
  -o /tmp/bootstrap.sh
less /tmp/bootstrap.sh                      # 10 секунд доверия к каналу
sudo bash /tmp/bootstrap.sh all
```

С нестандартным портом SSH:

```bash
sudo bash /tmp/bootstrap.sh all --port 2222
```

Компактнее, но канал не проверяете:

```bash
curl -fsSL https://raw.githubusercontent.com/pafthang/ubuntu-server-2604-setup/main/bootstrap.sh \
  | sudo bash -s -- all --port 2222
```

Оба варианта равнозначны по результату: во втором скрипт сам скачивает этапы
и генерирует временный `config.env` из переданных флагов.

#### Воспроизводимость: пинуйте коммит

Чтобы состояние сервера не зависело от будущих правок ветки, подставьте
в URL хэш коммита вместо `main`:

```bash
git ls-remote https://github.com/pafthang/ubuntu-server-2604-setup.git main
# → например: 1a2b3c4...   тогда:
https://raw.githubusercontent.com/pafthang/ubuntu-server-2604-setup/1a2b3c4/bootstrap.sh
```

#### Что произойдёт

1. **Подтверждение** — состав работ и целевой порт; отказ останавливает
   выполнение **до** любых изменений системы.
2. **Этап 10** — обновление системы, установка пакетов, fish/micro/helix/zellij/fzf,
   micro как редактор по умолчанию (`sudoedit`, `git commit`, `crontab -e`),
   fish станет login-shell со следующего логина.
3. **Этап 20 (hardening)** — drop-in конфиг sshd (порт, лимиты сессий;
   аутентификационные директивы не затрагиваются), UFW c правилом LIMIT для SSH,
   fail2ban (через systemd-journal), автообновления security, персистентность
   journald, часовой пояс, опциональный swap. Финальная сводка показывает
   фактические `port` / `passwordauthentication` / `permitrootlogin` — то,
   что оставил провижининг.

⚠️ Hardening переключает порт sshd и включает firewall. Запускайте удалённо
из живой сессии и **не закрывайте её**, пока вторым окном не проверите вход
по новому порту. Установленное соединение не рвётся — починить можно из него.

#### Флаги

| Флаг                    | Значение                    | По умолчанию |
| ----------------------- | --------------------------- | ------------ |
| `all\|packages\|harden` | полный прогон или один этап | `all`        |
| `--port N`              | порт sshd после hardening   | `22`         |
| `--yes`                 | пропустить подтверждение    | интерактивно |

Пример тестового прогона в контейнере (там нечего подтверждать интерактивно):

```bash
lxc launch ubuntu:24.04 bt && lxc exec bt bash
sudo bash bootstrap.sh all --yes
```

### Вариант B — поэтапно

Полный контроль между шагами:

```bash
git clone https://github.com/pafthang/ubuntu-server-2604-setup.git
cd ubuntu-server-2604-setup
cp config.env.example config.env    # при желании: SSH_PORT/TIMEZONE/SWAP

sudo ./10-packages.sh               # перелогиниться → окажетесь в fish
sudo ./20-hardening.sh              # UFW/fail2ban/автообновления/журнал
```

Можно запускать и через оркестратор теми же подкомандами:
`sudo bash bootstrap.sh packages`, `… harden`.
При запуске рядом с локальными файлами он использует их, а не сеть.

## Почему скрипты не управляют входом

Классическая схема «скрипт кладёт ключи → выключает пароли» имеет окно
самозапирания: между двумя действиями нужно доказать извне, что ключ реально
работает, иначе ошибка превращается в поездку к VNC-консоли провайдера.
Раньше для этого здесь стоял интерактивный гейт с прослушиванием журнала sshd.

Проще устранить само окно: доставка ключей происходит **до** первого запуска
скриптов — средствами создания машины. Тогда:

- аутентификация единообразно задаётся метаданными (одна точка правды для
  фермы машин);
- скриптам достаются задачи, где автоматизация безопасна: сеть, пакеты,
  службы; худшее последствие их сбоя — повторный запуск, а не потеря доступа;
- фактическое состояние входа всегда видно в итоговой сводке
  (`sshd -T | grep -E '^(port|passwordauthentication|permitrootlogin) '`).

Если образ провайдера пришёл с включённым парольным входом и вы хотите его
закрыть — готовые строки лежат закомментированными в
`/etc/ssh/sshd_config.d/60-hardening.conf`: раскомментируйте, убедившись,
что текущая сессия поднята по ключу, затем `systemctl restart ssh`.

## Конфигурация

Приоритет источников: аргументы CLI → переменные окружения → `config.env`.
В piped-режиме (`curl | bash`) файл генерируется автоматически из флагов.

| Параметр      | Где задаётся              | Значение                         |
| ------------- | ------------------------- | -------------------------------- |
| `SSH_PORT`    | `--port` / env/config.env | порт sshd после hardening        |
| `TIMEZONE`    | config.env                | часовой пояс; пусто = не трогать |
| `CREATE_SWAP` | config.env                | `true` → создать swapfile        |
| `SWAP_SIZE`   | config.env                | размер swapfile                  |

## Подключение после установки

На локальной машине заведите алиас в `~/.ssh/config` — дальше везде `ssh ams1`:

```bash
Host ams1
    HostName <IP_сервера>
    User root
    Port 22            # ваш SSH_PORT, если меняли
    IdentitiesOnly yes
```

Проверка, во что развернулся алиас: `ssh -G ams1 | grep -E '^(user|hostname|port) '`.
Алиасы работают и в `scp`, и в `rsync`.

## Если что-то пошло не по плану

Прервались где угодно — продолжайте соответствующим режимом:

```bash
sudo bash bootstrap.sh packages   # обновит/доустановит без вреда
sudo bash bootstrap.sh harden     # UFW/fail2ban/конфиги — идемпотентно
```

Частые случаи:

- **fish не стала активной** — она вступает в силу со следующего логина;
  текущая bash-сессия этому не помеха.
- **Ctrl-R/Ctrl-T в fish молчат** — старый fzf (< 0.48) без поддержки
  `--fish`; обновите пакет, интеграция подхватится сама.
- **Сменили порт и потерялись** — живое соединение не рвётся; из него:
  `ss -tlnp | grep sshd` покажет фактический порт.
- **Непосредственно через `curl … | bash` этапные файлы (10/20) не запускать** —
  piped-исполнение поддерживает только `bootstrap.sh`.

## Проверка после установки

| Действие                                                                 | Ожидание                              |
| ------------------------------------------------------------------------ | ------------------------------------- |
| `ssh root@host`                                                          | пускает по ключу, молча               |
| `sshd -T \| grep -E '^(port\|passwordauthentication\|permitrootlogin) '` | фактические порт и методы входа       |
| `ufw status verbose`                                                     | `Status: active`, порт SSH в LIMIT    |
| `fail2ban-client status sshd`                                            | отвечает, счётчики нулевые            |
| начать набирать команду в fish                                           | серая автоподсказка, `→` принимает её |
| `Ctrl-R` в fish                                                          | fuzzy-поиск истории                   |
| `journalctl -b -1` после ребута                                          | журнал прошлой загрузки читается      |
| `hx --health`                                                            | таблица языков helix                  |
| `zellij`                                                                 | интерфейс с подсказками клавиш внизу  |

После первого прогона рекомендуется `reboot`: могли приехать новые ядра.

## Ограничения и осознанные упрощения

- Работаем под **root** — конфиги уже лежат в `/root`; миграция на отдельного
  пользователя с sudo возможна позже отдельно.
- **Аутентификация вне зоны скриптов** — ключи/пароли задаёт провижининг
  при создании машины; см. соответствующий раздел выше.
- Бинарные релизы zellij/helix ставятся под **amd64/arm64** автоматически;
  на экзотической архитектуре скрипт остановится с понятной ошибкой.
- Бэкапы **не входят** сознательно: отдельный проект (restic/borg + внешний
  сторадж), по важности выше всего перечисленного здесь.
- Docker публикуемые им порты проводит мимо правил UFW — при добавлении
  контейнеров потребуется отдельная настройка.

## Идеи расширения

- **Ubuntu Pro** (бесплатно до 5 машин) → Livepatch: патчи ядра без ребутов;
- **cloud-init/Terraform-модуль** поверх репозитория — шаблон машины сразу
  с этим прогоном в `runcmd`;
- `starship` (промпт), `zoxide` (умный cd) — однострочные установщики;
- restic/borg → внешний сторадж.
