# ubuntu-server-2604-setup

Первичная настройка чистого Ubuntu Server (24.04+, включая 26.04)
одной командой или тремя шагами:

- базовые пакеты и инструменты диагностики;
- оболочка **fish** (автоподсказки из коробки) + fzf, zellij, micro, helix;
- доступ по SSH **только по ключам**, firewall **UFW**, защита от брутфорса
  **fail2ban**, автообновления security, персистентный журнал, опциональный swap.

Все скрипты **идемпотентны**: обрыв связи посреди прогона лечится повторным
запуском — продолжится с того же места без дублей.

> Работает под root на свежеустановленной системе. Ничего, кроме описанного,
> не трогает; все изменения — отдельными файлами (drop-in конфиги), родные
> конфиги дистрибутива не перезаписываются.

## Быстрый старт

### Вариант A — одной командой

Надёжнее — скачать, пробежать глазами, запустить:

```bash
curl -fsSL https://raw.githubusercontent.com/pafthang/ubuntu-server-2604-setup/main/bootstrap.sh \
  -o /tmp/bootstrap.sh
less /tmp/bootstrap.sh                      # 10 секунд доверия к каналу
sudo bash /tmp/bootstrap.sh all \
  --key-url https://github.com/pafthang.keys --port 22
```

Компактнее, но канал не проверяете:

```bash
curl -fsSL https://raw.githubusercontent.com/pafthang/ubuntu-server-2604-setup/main/bootstrap.sh \
  | sudo bash -s -- all --key-url https://github.com/pafthang.keys
```

Оба варианта равнозначны по результату: во втором скрипт сам скачивает этапы
и генерирует временный `config.env` из переданных флагов.

#### Воспроизводимость: пинуйте коммит

Чтобы состояние сервера не зависело от будущих правок ветки, подставьте
в URL хэш коммита вместо `main`:

```bash
git ls-remote https://github.com/pafthang/ubuntu-server-2604-setup.git main
# → например: 1a2b3c4...   тогда:
https://raw.githubusercontent.com/pafthang/ubuntu-server-2604-setup/1a2b3c4/bootstrap.sh
```

#### Что произойдёт

1. **Этап 10** — обновление системы, установка пакетов, fish/micro/helix/zellij/fzf,
   micro как редактор по умолчанию (`sudoedit`, `git commit`, `crontab -e`),
   fish становится login-shell (вступит в силу со следующего логина).
2. **Этап 20** — загрузка публичных ключей из `KEY_URL`, проверка формата,
   дедупликация, запись в `/root/.ssh/authorized_keys`.
3. **✋ Гейт доступа** — скрипт останавливается и ждёт (по умолчанию до 15 минут),
   пока вы откроете **второй терминал** и войдёте: `ssh root@<ip>`.
   Вход детектируется автоматически по журналу (`Accepted publickey`) —
   это доказательство извне, а не вопрос «у вас получилось?».
4. После подтверждения — финальное `[y/N]`, затем **этап 30**: закрытие паролей,
   drop-in конфиг sshd, UFW, fail2ban (через systemd-journal), автообновления
   security, персистентность journald, часовой пояс, swap.

Если за таймаут входа не случилось — hardening НЕ применяется, система остаётся
доступной как есть. Догнать позже: `sudo bash bootstrap.sh harden`.

#### Флаги

| Флаг                            | Значение                                         | По умолчанию    |
| ------------------------------- | ------------------------------------------------ | --------------- |
| `all\|packages\|access\|harden` | полный прогон или один этап                      | `all`           |
| `--key-url URL`                 | источник публичных ключей (URL или путь к файлу) | из `config.env` |
| `--port N`                      | порт sshd после hardening                        | `22`            |
| `--timeout SEC`                 | сколько ждать повторный вход на гейте            | `900`           |
| `--yes`                         | отвечать «да» на подтверждения                   | интерактивно    |
| `--skip-gate`                   | пропустить ожидание входа по ключу               | включён         |

⚠️ `--skip-gate` и `--yes` — только для тестов (LXC/CI), где второй SSH-вход
физически невозможен. На боевом сервере они отключают единственную защиту
от самозапирания.

Пример тестового прогона в контейнере:

```bash
lxc launch ubuntu:24.04 bt && lxc exec bt bash
sudo bash bootstrap.sh all --key-url ... --yes --skip-gate
```

### Вариант B — поэтапно

Полный контроль между шагами:

```bash
git clone https://github.com/pafthang/ubuntu-server-2604-setup.git
cd ubuntu-server-2604-setup
cp config.env.example config.env    # вписать KEY_URL, при желании SSH_PORT/TIMEZONE

sudo ./10-packages.sh               # перелогиниться → окажетесь в fish
sudo ./20-ssh-access.sh             # ⚠️ правило ниже
# ✋ вторая сессия: проверить вход по ключу, первую не закрывать!
sudo ./30-hardening.sh              # только после успешной проверки
```

Можно запускать и через оркестратор теми же подкомандами:
`sudo bash bootstrap.sh packages`, `… access`, `… harden`.
При запуске рядом с локальными файлами он использует их, а не сеть.

## Гейт доступа: почему так сложно

Ключи доставляются **тем же каналом, который затем закрывается**
(`PasswordAuthentication no`, firewall). Ошибка в порядке операций =
самозапирание. Поэтому единственное место, где автоматизация честно
останавливается — момент между «ключи положили» и «пароли выключили».
Подтверждение берётся не у пользователя (он может ошибаться), а у независимого
источника — журнала sshd.

Полностью убрать человека можно доставкой ключей **до** первого включения
машины — cloud-init/Terraform метаданными облака (`users.ssh_authorized_keys`).
Для фермы машин это правильный путь; для одного сервера гейт стоит ~60 секунд.

## Конфигурация

Приоритет источников: аргументы CLI → переменные окружения → `config.env`.
В piped-режиме (`curl | bash`) файл генерируется автоматически из флагов.

| Параметр      | Где задаётся                   | Значение                         |
| ------------- | ------------------------------ | -------------------------------- |
| `SSH_PORT`    | `--port` / env / config.env    | порт sshd после hardening        |
| `KEY_URL`     | `--key-url` / env / config.env | источник публичных ключей        |
| `TIMEZONE`    | config.env                     | часовой пояс; пусто = не трогать |
| `CREATE_SWAP` | config.env                     | `true` → создать swapfile        |
| `SWAP_SIZE`   | config.env                     | размер swapfile                  |

GitHub отдаёт публичные ключи одним запросом — единая точка правды для всех
ваших серверов: `https://github.com/pafthang.keys`
(добавлять ключи удобнее на GitHub → Settings → SSH keys, серверы при этом
не трогаются вовсе).

## Подключение после установки

На локальной машине заведите алиас в `~/.ssh/config` — дальше везде `ssh ams1`:

```bash
Host ams1
    HostName <IP_сервера>
    User root
    Port 22            # ваш SSH_PORT, если меняли
    IdentitiesOnly yes
```

Проверка, во что развернулся алиас: `ssh -G ams1 | grep -E '^(user|hostname|port) '`.
Алиасы работают и в `scp`, и в `rsync`.

## Если что-то пошло не по плану

Прервались где угодно — продолжайте соответствующим режимом:

```bash
sudo bash bootstrap.sh packages   # обновит/доустановит без вреда
sudo bash bootstrap.sh access     # доложит отсутствующие ключи
sudo bash bootstrap.sh harden     # требует непустой authorized_keys; откажется иначе
```

Частые случаи:

- **fish не стала активной** — она вступает в силу со следующего логина;
  текущая bash-сессия этому не помеха.
- **Ctrl-R/Ctrl-T в fish молчат** — старый fzf (< 0.48); инструкция PPA
  комментарием в конце установки пакетов в `10-packages.sh`.
- **Сменили порт и потерялись** — живое соединение не рвётся; из него:
  `ss -tlnp | grep sshd` покажет фактический порт.
- **Непосредственно через `curl … | bash` этапные файлы (10/20/30) не запускать** —
  piped-исполнение поддерживает только `bootstrap.sh`.

## Проверка после установки

| Действие                                   | Ожидание                              |
| ------------------------------------------ | ------------------------------------- |
| `ssh root@host`                            | пускает без пароля                    |
| `ssh -o PubkeyAuthentication=no root@host` | `Permission denied (publickey)`       |
| `ufw status verbose`                       | `Status: active`, порт SSH в LIMIT    |
| `fail2ban-client status sshd`              | отвечает, счётчики нулевые            |
| начать набирать команду в fish             | серая автоподсказка, `→` принимает её |
| `Ctrl-R` в fish                            | fuzzy-поиск истории                   |
| `journalctl -b -1` после ребута            | журнал прошлой загрузки читается      |
| `hx --health`                              | таблица языков helix                  |
| `zellij`                                   | интерфейс с подсказками клавиш внизу  |

После первого прогона рекомендуется `reboot`: могли приехать новые ядра.

## Ограничения и осознанные упрощения

- Работаем под **root** — конфиги уже лежат в `/root`; миграция на отдельного
  пользователя с sudo возможна позже отдельно.
- Бинарные установки zellij/helix рассчитаны на **x86_64**; для arm64 поправьте
  URL релизов в функциях `install_*`.
- Бэкапы **не входят** сознательно: отдельный проект (restic/borg + внешний
  сторадж), по важности выше всего перечисленного здесь.
- Docker публикуемые им порты проводит мимо правил UFW — при добавлении
  контейнеров потребуется отдельная настройка.

## Идеи расширения

- **Ubuntu Pro** (бесплатно до 5 машин) → Livepatch: патчи ядра без ребутов;
- **cloud-init / Terraform** — доставка ключей вне SSH убирает гейт полностью;
- `starship` (промпт), `zoxide` (умный cd) — однострочные установщики;
- restic/borg → внешний сторадж.
